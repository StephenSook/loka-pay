# LOKA Pay website (`web/`)

Next.js (App Router, TypeScript) with Tailwind CSS, managed with pnpm. It will serve https://zerobars.us.

Pages today:

| Path | What it shows |
|---|---|
| `/` | What LOKA Pay is, the sandbox chip, the build status, the judge door button and links to every page |
| `/judge` | The judge door: a numbered three-minute itinerary, the program's facts read live from devnet, the TestFlight status and each workflow's result on main, read from GitHub's API by the server |
| `/live` | The program's transactions, read by the browser straight from devnet (`getSignaturesForAddress`, `getTransaction`, then a `logsSubscribe` WebSocket). It keeps the newest 100 rows, and after a reconnect it reads the history again and retries rows whose details it had given up on. A transaction answer it cannot read marks only its own row "Details unavailable". The socket also carries a `slotSubscribe` heartbeat, so with nothing arriving for 10 s the connection chip says "No update for N s" instead of Live, and Live again when traffic resumes. `/live?kiosk=1` uses large type |
| `/verify` | Checks a payment receipt in the visitor's browser (PAYMENT-V1 section 4.9): from a `#r=<base64url>` link or pasted text, plus a button that loads the published test receipt. Under a receipt that verifies, "Play the attacker" lets the visitor edit the note's amount or payee and runs the same check on the edited bytes, in the tab |
| `/proof` | Claims, each Live only from a current read with its evidence linked and the read's time and age shown (the verifier is Available, a page to run yourself), proof of reserves from the program's accounts at one slot, and "Built this weekend" from GitHub's compare API |
| `/trust` | The threat model in plain words: what the program checks, what the protocol does not promise, custody, and the upgrade authority read from chain |
| `/call` | "Call me when it settles" (PLAN.md 3.9): a visitor enters their own US number (one validator, `lib/call-shared.ts` `isCallableUsNumber`, used by the page and the server, refuses Canada, the Caribbean and other non-US NANP codes, toll-free, premium and special numbers), and an ElevenLabs voice placed through Vonage reads a real settled payment from devnet. "Call me now" reads the program's latest settled payment; "Call me when the next payment settles" watches the program from the browser (as `/live` does) and sends the new payment's signature once it settles |
| `/watch` | One allowance, read by the visitor's own browser straight from devnet (PLAN.md 3.85): `/watch?a=<allowance id>` (or the payer phone's `LOKA-ALLOWANCE:<id>` code). The allowance's address is worked out in the browser from its id (`lib/pda.ts`, the seeds `open.rs` uses), so no account scan is needed. A meter shows its cap, settled so far, what is left and the serials used (`lib/allowance-read.ts`, decoded with `decodeAllowance`), and below it the newest `redeem_note` transactions whose allowance account (`accounts[1]`) is this allowance's (a spent note replayed for another allowance with this one added as an extra account is not listed): settled ones Paid with the amount and serial from their `NoteRedeemed` event for this allowance, failed ones Refused only when that `redeem_note` is the failing top-level instruction: named by the program's log line, or by its error code (`lib/program-errors.ts`; a code at another program's index, such as a 6011 at the precompile's, is never named). With no payment among the newest 8 it says so, and that the meter's serials point further back. It reads `getAccountInfo` and `getSignaturesForAddress` in one batch every 5 s while the page is visible, reads new transactions with `getTransaction` under `/live`'s pacing, and sends nothing while the page is hidden (`lib/watch.ts`). `/judge` step 3 shows a QR code that opens it for the demo payer's allowance (`lib/facts.ts` `DEMO_ALLOWANCE_ID`) |
| `/send` | Send sandbox money to a payer phone (PLAN.md 3.3, web half): a form for the recipient allowance id and an amount up to 1.00, posted from the visitor's browser to `POST /v1/remittances` on api.zerobars.us; the returned allowance certificate is checked in the browser against the pinned server key and drawn as a QR code. On only while the server's health check lists that route as registered |
| `/privacy` | The privacy policy. Also the App Store Connect privacy policy URL for the TestFlight build |

Other pages arrive with the tasks that build them (see `PLAN.md`). Claims follow the code: no page describes a feature that is not built and tested.

## `/send`, sandbox remittances (PLAN.md 3.3)

- The server half is `POST /v1/remittances` (protocol/API-V1.md section 9, `server/src/remit/remittance.ts`, off until its configuration is set). Request: exactly `{recipientAllowanceId, amountUnits}`, both decimal strings; `amountUnits` at most `1000000` (1.00 sandbox USDC). The browser sends only the `Content-Type` header and no credentials, because the server's CORS (server/src/app/app.ts) allows `https://zerobars.us` and `https://www.zerobars.us` with the `Content-Type` header only. A Vercel preview or localhost origin is refused by that CORS, so the form cannot reach the real server from a preview build; that is expected, not a bug.
- On or off (`lib/send-server.ts` `sendAvailability`): our server reads `https://api.zerobars.us/api/health` (the same cached read as `/proof`, `lib/settlement.ts`). The form is on only when the latest read succeeded, `ok` is true and `phase3Routes["/v1/remittances"].registered` is true. A health answer without `phase3Routes` (a server deployed before the Phase 3 routes) is off. A POST answering `404 unknown_route` turns the form off too. Off shows "Sending is off on the server right now." with the reason, and no form.
- Answers (`lib/remittance.ts` `classifyAnswer`) are told apart by status and `error` name, never the message: 201 new, 200 the first send's terms repeated (one live send per recipient allowance); 202 pending, after which the page sends the SAME request again after `retryAfter` (held to 1 to 10 s), starting no new request more than 30 s after the first (each request waits up to 20 s for its answer), then stops with "Still pending" and a button to send it again; 409 `remittance_failed` with its transaction's explorer link; 422 `amount_cap` and `unknown_allowance`; 429 `budget_exhausted` and `rate_limited`; 503 `chain_unavailable` (safe to send again); 400 `bad_json`; 500 `internal_error`. The cross-origin answer does not expose `Retry-After`, so the page does not rely on it.
- The recipient field accepts the phone's code `LOKA-ALLOWANCE:<id>` (exact, case-sensitive prefix) or the bare id, as docs/ALLOWANCE-ID-QR.md defines them: a canonical decimal u64, no sign, no leading zero, at most 18446744073709551615, whitespace allowed only around the whole text. Anything else is refused by name in the page and never sent.
- The certificate (`allow`, an ALLOW wire in unpadded base64url) is checked with `verifyAllowWire` from `@lokapay/protocol` against `config/pins.json`'s `serverEd25519PublicKey`, then against the answer's allowance id and earmarks and the browser's clock (an expired one is refused, as the phone refuses it). The headline says "Allowance opened on devnet" only for a verified certificate; otherwise "Server says opened; certificate not verified". When the certificate's cap differs from the amount entered (a repeat, or another request for the same recipient got there first), the page says so. Only a verified certificate is drawn, as a QR code (uqr, level M, in the browser) of exactly `L1|P|1|A|<allow>` (PAYMENT-V1 section 5); otherwise the page says Not verified and why.
- Tests: `unit/remittance.test.ts` (input rules, error names, the pending loop with a fake clock, certificate checks), `unit/qr.test.ts` (the drawn modules decoded by jsQR), `unit/send-server.test.ts` (on or off, the key seam) and `e2e/send.spec.ts`, where every POST is answered by Playwright route interception, never by a real server. `SETTLEMENT_TEST_SERVER_KEY` lets the e2e server check certificates against the published test vector key, only in the e2e test mode and never in a deployed production build.

## Chain and GitHub reads (`/judge`, `/live`, `/proof`, `/trust`)

- `lib/pins.ts` bundles every public field of `config/pins.json` with a static import and checks each address (32 bytes of base58, cluster `devnet`). A missing or malformed file fails `next build`. (`lib/deployment.ts` stays as it is for `/verify`, which needs the server key.)
- `lib/solana.ts` is a small JSON-RPC client (8 s timeout, one retry on a timeout, network error or 5xx; HTTP 429 is reported, not retried). Server reads (`lib/server-rpc.ts`) make no retries and share one 10 s limit across every call of a read, so a hanging node gives the page its honest failure within that limit instead of holding it until the host's function timeout. `NEXT_PUBLIC_SOLANA_RPC_URL` and `NEXT_PUBLIC_SOLANA_WS_URL` name the endpoints the browser uses on `/live`; they are inlined into every visitor's page, and a provider can carry its API key in the path as well as the query, so each accepts only an allowlist of public endpoints that need no key (`https://api.devnet.solana.com` and its `wss://` twin) and any other URL fails the build with a `PublicEndpointError` that names the variable, never its value. `SOLANA_RPC_URL` (`lib/server-rpc.ts`) is the endpoint for the server reads and is never sent to a browser, so a keyed provider URL goes there. `/privacy` names the hosts this build actually uses. All of them are listed in `.env.example`.
- The e2e test seam (`lib/test-upstream.ts`, server only): `GITHUB_API_URL` may replace `https://api.github.com` only with a local endpoint, and `SOLANA_RPC_URL` may name a local endpoint, only while `LOKA_E2E_UPSTREAM=1` is set; a deployed production build (`NODE_ENV=production` with `VERCEL` set) refuses both with an error naming the variable, so a stand-in's answers never count as devnet or GitHub evidence on the real site. `SOLANA_RPC_URL` still accepts any real provider URL, keyed or not. A real `GITHUB_TOKEN` goes only to `https://api.github.com` itself, never to another host or over http; in test mode the only token ever sent is the e2e stand-in's test token, and only to the stand-in.
- `GITHUB_TOKEN` (optional, server only, `lib/github.ts`): when set, the server's GitHub reads (each workflow's result on main for `/judge` and `/proof`, and the commit count) send it as `Authorization: Bearer`, so they run under the token's limit instead of GitHub's 60 requests an hour per IP, which shared hosting addresses can use up. A fine-grained token with read-only access to public repositories is enough. It has no `NEXT_PUBLIC` prefix, is read only by `lib/github.ts`, is never logged or shown, and `unit/server-only.test.ts` fails if a client module can reach the modules that read it.
- `lib/vault.ts` decodes the program's accounts (`programs/loka_vault/src/state.rs`), events, `open_allowance` arguments, the upgradeable loader's accounts and SPL token accounts. `lib/logs.ts` reads log lines into instruction names, event amounts and Anchor's named errors, attributing each line to the program on top of the call stack.
- `/judge`, `/proof` and `/trust` render per request and read on the server through `lib/chain.ts` and `lib/github.ts`. Results are cached with the time they were read (`lib/cached-read.ts`, `unstable_cache`): 30 seconds for devnet, 5 minutes for GitHub, and an entry older than that is read again. A read made past the cache is kept in the server process with its own time, so the next page views use it instead of each reading again. Every value is shown with its time and its age when the page rendered; a page re-stamps all of its reads at one render time after the slowest has arrived (`lib/read-state.ts`). A read is current when it is at most 10 s old for devnet or 60 s for GitHub, with no newer read that failed; only a current read makes a claim Live on `/proof` (which asks for one, reusing a kept read under 7 s or 45 s old), and `/trust` says upgradeability in the present only from one. A failed read is never cached and never replaced by a typed-in value; the page says what failed and when. When an earlier good read exists, it is shown marked stale with the failed read's reason and time ("Not current. Last good read ..."), the read-backed claims say Not checked, and the commit count is not shown at all (PLAN.md 3.60: never a stale count), only the time of the last good read.
- Every upstream read goes through one ReadGate per server process (`lib/read-state.ts`): page views that want a running read share it, each read has a budget (3 per 10 s for devnet, 3 per minute for GitHub), and a rate-limited answer pauses that read (10 s, 60 s) instead of being retried. A read the gate does not make leaves the last good read on the page, with its age and the reason.
- Public devnet allows 10 `getProgramAccounts` and 10 `getTransaction` calls per 10 seconds per IP, refuses `getProgramAccounts` inside a JSON-RPC batch, and refuses a batch that repeats `getAccountInfo` or `getTokenAccountBalance`. So the program's accounts are listed with one unfiltered `getProgramAccounts` call returning each account's 8-byte discriminator, fixed accounts are read with `getMultipleAccounts`, and `/live` reads every transaction's details through one queue: one batch request at a time, newest first, at most 8 calls per 11 s, and nothing for 11 s after a rate-limited answer.
- Proof of reserves lists the program's accounts, reads the vault token account and every allowance and merchant in one `getMultipleAccounts` call (one slot), then lists the accounts again at that slot to confirm none was missed.

## `/verify`, the protocol library and `config/pins.json`

- `@lokapay/protocol` is `protocol/lib`, linked with `link:../protocol/lib`. A linked package's own dependencies are not installed by this project's install, so the `postinstall` script runs `pnpm install --frozen-lockfile --prod` in `protocol/lib`. `next.config.ts` sets `turbopack.root` to the repository root, because Turbopack resolves nothing outside its root and `/verify` also imports `protocol/vectors/payment-v1.json`.
- The status shown always comes from the signed confirmation, after `verifyReceipt` passes. On a failure the page names the error code and the check it came from.
- `lib/deployment.ts` reads `config/pins.json` at build time. While the file is missing it exports `null`, and receipts other than the test vectors get the notice that the server key is not published. When the file exists, the page reads these fields (others are ignored), and a present but unreadable file fails the build:

  ```json
  {
    "cluster": "devnet",
    "programId": "<base58, 32 bytes>",
    "mint": "<base58, 32 bytes>",
    "serverEd25519PublicKey": "<64 hex characters, or base58 of 32 bytes>"
  }
  ```

- A receipt whose note carries the vector-only program id is checked against the test deployment and test server key in `protocol/vectors/payment-v1.json` and labelled as a test vector made from public test keys.
- "Play the attacker" (`components/attacker-panel.tsx`, `lib/attacker.ts`, PLAN.md 3.52): under a verified receipt it shows the note's ten fields decoded from its 141 bytes, each with its byte range. The visitor changes the amount or picks a test merchant from the vectors file as the payee; the page encodes the edited note with the protocol library (`encodeNote`), counts the changed byte positions, and passes the edited receipt to `evaluateBytes`, the function that verified the original. An edit fails with `bad_signature` in the note check, and Undo restores the signed bytes. It makes no request (`e2e/verify-attacker.spec.ts` intercepts every request while editing and expects none). Sending an edited note to devnet is not built.

## `/call`, the phone call (PLAN.md 3.9)

- `POST /api/call` with `{to, lang, signature?, code?}` (`lib/call-server.ts`, Node runtime, no new package: `node:crypto` and `fetch` only). Calls are off (503 `calls_off`) unless `LOKA_VONAGE_APPLICATION_ID`, `LOKA_VONAGE_PRIVATE_KEY_B64`, `LOKA_VONAGE_FROM_NUMBER`, `ELEVENLABS_API_KEY` and `LOKA_CALL_SECRET` (at least 32 bytes) are all set; `LOKA_CALLS_OFF=1` turns them off. All are server only and listed in `.env.example`.
- The payment comes from devnet through the server's RPC endpoint, decoded by `lib/logs.ts` (`lib/call-payment.ts`): only a transaction that succeeded, names the program and logs `redeem_note` with a `NoteRedeemed` amount counts. Without a signature, the newest of the program's last 25 signatures (failed ones skipped, at most 8 read in full); with one, it must have settled within 15 minutes (409 `too_old`). None: 404 `no_settled_payment`. A failed read: 502 `chain_read_failed`, never 404.
- Desk code: `LOKA_CALL_CODE` is required for calls on any host, at least 8 letters and digits with at least one of each, or calls are off (503 `calls_off`, reason `not set: LOKA_CALL_CODE`). Nothing relies on `VERCEL_ENV` for this, since a host can hide its own variables. The only exception is `LOKA_CALL_TEST_MODE=1`, an explicit local test run, which is refused wherever `VERCEL` or `VERCEL_ENV` is set. Every request must carry the code as `code`, compared in constant time; missing or wrong is 403 `wrong_code`. Wrong codes never count against a number or the site, so nobody can lock judges out with bad codes; they go to their own limiter, 10 per address in 10 minutes, after which that address's wrong codes get 429 while a correct code still goes through, since the code is compared first (the code's entropy and this per-client limit bound guessing; there is no site-wide failure cap, which would let one attacker lock everyone out; the production code is 8 characters from a 31-symbol alphabet, about 8.5 x 10^11 codes, and can be rotated in Vercel at any time), keyed by HMAC-SHA256(a random per-process secret, the client's address), never the address itself. The address is Vercel's `x-vercel-forwarded-for`, then `x-real-ip`, never the client-writable `x-forwarded-for`; a request with neither is refused (400), and only a local test run uses one shared key.
- Order: the body is checked, then the kill switch and the configuration, then the desk code, then the caps, and only then is devnet read and Vonage asked. Caps (`lib/call-limits.ts`): a request naming a signature this number was already called about is refused first, with no reservation and no devnet read. Otherwise a request with the right code reserves one slot per number (2 per 30 minutes, keyed by HMAC-SHA256(`LOKA_CALL_SECRET`, number)) and one for the site (30 an hour) before any devnet read, and both stay reserved whatever happens next; then one call per number and payment, remembered for 24 hours. A request refused earlier (bad body, calls off, wrong code) reserves nothing. 429 `rate_limited` with `Retry-After`. Every map and cache has a maximum size and expiry. `unit/call.test.ts` has one table row per rule.
- The desk code does not prove that the caller owns the number: a holder of the code can make our number ring any US number, within the caps. That risk is accepted; the page says "Only enter your own number", and the bounds are the desk code, US numbers only, the caps and the Vonage destination limits.
- These caps live in each server instance's memory, so on Vercel they are weak: every instance counts on its own and a new one starts at zero. The real bounds are the desk code, the Vonage account's balance and destination settings, and `LOKA_CALLS_OFF`. There is no database, on purpose.
- Vonage gets an RS256 JWT made with `node:crypto` and an NCCO that streams `GET /api/call/audio?p&m`: `p` is base64url JSON of the payment details and `m` its HMAC-SHA256, checked in constant time, valid 10 minutes. That route has ElevenLabs (`eleven_v4`, voice "Sarah" unless `LOKA_ELEVENLABS_VOICE_ID` is set) read `lib/call-speech.ts`'s text and returns the MP3, kept in memory until the link expires because Vonage may fetch twice. `POST /api/call/event` answers 204 and reads nothing.
- The number is never logged, written to disk or returned: no handler logs, each catches its own errors, and `unit/call.test.ts` captures the console across a full call and requires zero appearances of the number.
- Test seam: `LOKA_VONAGE_API_URL`, `LOKA_ELEVENLABS_API_URL` and a local `LOKA_PUBLIC_ORIGIN` work only in the e2e test mode and never in a deployed production build, like `GITHUB_API_URL`. The e2e stand-in answers for Vonage and ElevenLabs, and `playwright.config.ts` makes a fresh RSA key and secret for each run (never committed), sets a valid desk code, and sets `LOKA_CALL_TEST_MODE=1` because Playwright's requests carry no Vercel address header.

## Commands

Node 22 and pnpm 12.3.4 (the version in `packageManager`; Corepack or `pnpm self-update` gets it).

```sh
cd web
pnpm install --frozen-lockfile
pnpm dev                 # http://localhost:3000
pnpm lint                # ESLint (eslint-config-next)
pnpm typecheck           # next typegen, then tsc --noEmit
pnpm build               # production build
pnpm test:unit           # decoder and parser unit tests (unit/), no browser, no server

# Playwright: builds, serves on http://127.0.0.1:3100 and :3101, runs chromium and webkit
pnpm exec playwright install chromium webkit   # once
pnpm test:e2e
```

The e2e tests read the server pages against known values: `e2e/global-setup.ts` starts a local stand-in for devnet's JSON-RPC and GitHub's API (`e2e/fixtures/upstream.ts`, port 3190, every account and answer a labelled test fixture), and `playwright.config.ts` starts the build twice, both in the test mode (`LOKA_E2E_UPSTREAM=1`): on 3100 with `SOLANA_RPC_URL`, `GITHUB_API_URL` and the test `GITHUB_TOKEN` pointing at the stand-in, so the success path (facts, Live claims, exact reserves, the commit count, each workflow's result) is asserted every run; and on 3101 with both endpoints at a port where nothing listens, so the failure path is asserted every run too. Cache keys include a digest of the endpoint, so the two servers never share a cached read. `/live` still reads real devnet from the browser.

CI (`.github/workflows/web.yml`) runs the same steps, each on its own exit code. With `CI` set, Playwright skips its own build because the workflow builds in the step before. The unit tests run there too: `playwright.config.ts` includes them as its `unit` project, which needs no browser.

## Telemetry and tracking

- Next.js telemetry is off in CI (`NEXT_TELEMETRY_DISABLED=1` in the workflow). Locally, run `pnpm exec next telemetry disable` once, or export `NEXT_TELEMETRY_DISABLED=1`.
- No analytics, telemetry or error-tracking packages, and no cookies. `e2e/judge.spec.ts` fails if `/` or `/privacy` sets a cookie or requests anything from another origin. `e2e/judge-door.spec.ts` checks the same for `/judge`, `/proof` and `/trust` (the workflow results on `/judge` are read by the server, not loaded as images from github.com), and leaves `/live` free to reach devnet (the privacy page says so).
- Fonts (Bricolage Grotesque, Figtree) are committed in `app/fonts` and loaded with `next/font/local`, so neither a build nor a page load contacts another site for them.

## Design tokens

All tokens live in `app/globals.css` (CSS variables plus the Tailwind `@theme`), so every page reuses them:

- Paper `#FBF8F3` background, ink `#102A43` text, borders and hard shadows. Dark mode (from `prefers-color-scheme`) flips them to `#14163A` and `#FFF8EC`, never pure black.
- Display: Bricolage Grotesque 800, letter-spacing -0.03em (every `h1` to `h3`). Body: Figtree 500.
- 2 to 3 px ink borders, hard offset shadows with no blur (`shadow-hard` 4 px, `shadow-hard-lg` 6 px), capsule chips, an ink pill call to action.
- Money states, each shown with a word AND an icon (`components/chips.tsx`, `StateChip`): Pending `#FFB020`, Received `#9FE3E0`, Paid `#1FA35B` (white text only on `#0F7A40`), Warning fill `#FFD9D7` with border `#B4232A`, Failed `#E5484D` (white text only on `#B4232A`).
- Grid children get `min-w-0` (a base rule in `globals.css` and in the markup), so long content cannot widen the page.
