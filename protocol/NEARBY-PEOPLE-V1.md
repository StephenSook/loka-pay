# Nearby people v1 (LP1)

LP1 is direct-link control alongside, not inside forwarding of, unchanged packet-v0 chat. Frames begin ASCII LP1H (hello) or LP1E (encrypted control). Older peers may ignore/reject these control frames; ordinary v0 messages stay unchanged. LP1H contains `nonce-uuid|canonical-base64-public-key`. LP1E contains raw packet-v0 bytes, encrypted to the hello's key and signed by the responding device. Its plaintext is either `LP1|P|nonce-uuid|base64-name` authenticated `LP1|X` visibility withdrawal, or existing LC1 request/accept/ack/decline content. Names follow LC1 validation and are self-chosen, not verified people. Public keys and traffic metadata remain observable; profile names are encrypted. Profiles are shared only while people discovery is enabled.

The receiver accepts a profile only for its own live per-link challenge, addressed to its key, signed by the profile key. This establishes key possession in response to a challenge; it does not prove proximity or prevent a forwarding/wormhole attack. No contact trust follows from a profile. Unknown chat/media still uses the existing trusted-sender gate. LC1 controls require an already established profile on that link with the same key. They are never rendered as chat text.

Bounds: 4096-byte control frame, 32 active links/profiles, 32 request records (16 inbound), 128 persistent blocks, 5-minute requests, global admission 32 frames per 10 seconds. Hello retries every 30 seconds until a profile is obtained; outstanding challenges live 60 seconds. Profiles expire on link-down or visibility withdrawal; connection loss never marks personal messages delivered. Consent retry every 15 seconds retains the original request deadline. State is encrypted at rest and saved before replies or contact authorization. Restart replays committed local approval idempotently; failure to load/save disables this control flow. Declines remain tombstones until request expiry. Blocking persists beyond expiry. Forgetting a contact blocks request replay. Simultaneous requests converge by using the lower request UUID, preserving the fact both users explicitly requested a chat.

One-sided requests require recipient Accept. Sender verifies A against its pending request/key/deadline and returns K. Receiver imports after its explicit acceptance; sender imports after matching acceptance; acknowledgement marks mutual protocol completion. A lost acknowledgement cannot undo explicit consent. Duplicate requests/replies are idempotent. At expiry, uncompleted requests stop retrying; explicit contact trust already committed remains until removed. QR trust remains available. No backend required.


## Ephemeral typing — preview 0.6.29

Encrypted LP1E plaintext `LP1|T|<canonical nonnegative epoch milliseconds>|<0 or 1>` is an optional direct-link activity hint. It contains no draft text. The receiving key must already be a trusted contact and match the current link's challenged profile. It never enters the mesh, persistent outbox, history, notification or receipt system. Older implementations ignore unknown LP1 content.

Sending requires a profile challenge/response completed within two seconds during the last minute; otherwise a bounded hello refresh is attempted and the hint is skipped. This checks recent responsiveness, not bandwidth or radio strength. No typing promises over relays or weak/stalled routes. Repeated activity is limited to once per four seconds; an explicit stop can be sent immediately. Hints expire at most eight seconds after their sender timestamp. Accept at most two seconds of positive clock skew; older/out-of-order/replayed timestamps are ignored. Per-peer timestamp maps are bounded to 32 and prune inactive entries. Disconnect clears the visible hint. UI stops after four seconds without input, on send/empty draft and on leaving/backgrounding the conversation; expiry covers lost stop frames. A blocked transport may drop/delay a hint, which then expires rather than being replayed as chat.

Ordinary message encryption is unchanged: recipient-key packet-v0 encryption and sender signature protect content from intermediate relays. This update adds no new cryptographic algorithm or forward-secrecy claim. Video/voice calling, measured sustained throughput/loss/jitter, and peer call-capability negotiation remain unimplemented; no call recommendation should be inferred from RSSI or this small control round trip.

## Bundled avatar metadata — preview 0.6.57

Optional encrypted LP1E content `LP1|I|<profile-challenge-uuid>|<canonical nonnegative epoch milliseconds>|<avatar-id>` accompanies the unchanged four-field LP1 profile response. The ID is exactly `avatar_0` through `avatar_41`, or `-` to clear the bundled portrait. Both platforms ship identical PNG bytes for these permanent IDs; see [catalog hashes](test-vectors/avatar-catalog-v1.json). Never renumber/reassign an ID. Future artwork needs new IDs and a reviewed catalog extension. No filename supplied by a peer is loaded from disk, and no remote URL is fetched.

The receiver verifies the existing recipient-addressed signature/encryption envelope first. It then requires a challenged profile with the same device key on the same link, matching the nonce of that accepted profile; a strictly increasing per-link timestamp within the last 60 seconds (at most 2 seconds ahead); and the exact whitelist. Unknown IDs, malformed timestamps, wrong keys/nonces, replays, withdrawn profiles and unbound links are ignored. Avatar state has the existing 32-link bound and is cleared on disconnect. The new content does not authorize a contact.

Sending requires people visibility enabled. One metadata control accompanies each hello/profile response; subsequent changed selections are sent on the existing tick, at most once per two seconds per link. Unchanged selections generate no additional periodic traffic. These are best-effort direct-link updates, with a fresh exchange on reconnect; this extension adds no acknowledgements or relay forwarding. The short ID saves image payload bytes, but the existing signed/encrypted packet and transport framing still contribute network overhead. Camera/library photos remain local; they send `-` and need a separate reviewed distribution flow.

Older LP1 peers ignore the unknown optional control while still receiving the original name/profile and consent frames. Packet-v0/v1/v2/v3 message schemas, cryptographic primitives, routing and personal-message trust remain unchanged. Saved friends can retain their last received bundled portrait locally by device fingerprint; unknown nearby profiles remain ephemeral. Local aliases are not overwritten.
