# LOKA Pay payment protocol, version 1

Status: draft for the event (task 1.2). Owner: Claude; reviewer: Khadim. Changes after merge follow the contract rule in `AGENTS.md`: announce in `PLAN.md` first, and start the commit subject with `⚠️ CONTRACT`.

Test vectors: `protocol/vectors/payment-v1.json`, generated by `tools/vectors/gen.mjs` (`pnpm run gen`; CI runs `pnpm run check` and fails if the file is stale). Every implementation (Swift, Kotlin, TypeScript, Rust) tests against that file. The `ios/LokaPay` package tests (task 1.5) also check the vectors with Apple CryptoKit.

Everything in this protocol is sandbox: Solana devnet and devnet USDC, which has no monetary value.

## 1. Roles and flow

- **Payer:** a phone holding a P-256 key (Secure Enclave on iPhone, hardware Keystore on Android). It signs notes.
- **Merchant:** a phone holding its own P-256 key. It receives notes over the LOKA mesh, signs an acknowledgement, and later uploads the note for settlement.
- **Server:** the settlement API. It holds an Ed25519 key that signs certificates and confirmations, pays Solana fees, and relays notes to the program. It cannot forge a payer's note.
- **Program:** the `loka_vault` Solana program. It verifies the payer's P-256 signature through the secp256r1 precompile and moves the money.

Baseline flow:

1. Before going offline, the payer's allowance is opened on chain and the payer phone receives an allowance certificate (`A`).
2. Offline, the payer signs a note (`N`) for a merchant and sends it over one Bluetooth hop.
3. The merchant verifies the note offline, checks its own offline limit, shows "Received, pending (sandbox)", and returns a signed acknowledgement (`Y`).
4. When the merchant has signal, it uploads the note and acknowledgement (`POST /v1/notes`). The server builds a transaction with the precompile instruction and `redeem_note`.
5. The server returns a signed confirmation (`S`). The merchant shows "Paid (sandbox)" and passes a receipt (`X`) back to the payer.

## 2. Encoding rules

- Integers are big-endian unless this document says little-endian (only the precompile offsets in section 7 are little-endian).
- `u8`, `u16`, `u64` are unsigned; `i64` is signed two's complement. Times are `i64` unix seconds, UTC.
- Every signed structure starts with a 16-byte ASCII domain prefix of the form `LOKA-PAY-XXXX-V1`.
- Every signed structure binds the program id (32 bytes), the cluster id (`u8`: 0 devnet, 1 mainnet) and the mint (32 bytes), directly or through the note id. A structure signed for one deployment never verifies on another.
- Variable-length fields are `u16` length-prefixed. Nothing signed is joined with a separator.
- **Key hash:** `sha256(compressed public key)`, where the compressed key is the 33-byte SEC1 form (`0x02` or `0x03`, then the 32-byte X coordinate).
- **Note id:** `sha256(NOTE_V1)`, over the 141 note bytes only (not the signature).
- Decoders read exact lengths. A structure with missing or trailing bytes is invalid.

## 3. Signatures

**P-256 (payer and merchant).** ECDSA over curve P-256 with SHA-256, computed over the full structure bytes, prefix included.

- Signature on the wire: 64 bytes, `r || s`, each a 32-byte big-endian integer with leading zeros kept.
- `r` and `s` must be in `[1, n - 1]`, and `s` must be at most half the order (low-S). The Solana precompile rejects anything else.
  - `n = ffffffff00000000ffffffffffffffffbce6faada7179e84f3b9cac2fc632551`
  - `n / 2 = 7fffffff800000007fffffffffffffffde737d56d38bcf4279dce5617e3192a8` (a signature is valid only if `s <= n / 2`)
- Signers normalize: if `s > n / 2`, replace it with `n - s`, encoded again as exactly 32 bytes. Assume the platform library does not do this (CryptoKit and the Android Keystore do not promise low-S).
- iOS: sign the raw structure bytes with CryptoKit's data API (`signature(for: Data)`), never the digest overload, because the precompile hashes the message itself. Use `rawRepresentation` (64 bytes), not DER.
- Android: the Keystore returns DER. Convert it to 64-byte `r || s`, then normalize to low-S.
- Public key on the wire: 33-byte compressed SEC1.

**Ed25519 (server).** Standard Ed25519 (RFC 8032, no prehash) over the full structure bytes. The 32-byte public key is in `config/pins.json`.

## 4. Structures

Byte offsets are zero-based.

### 4.1 NOTE_V1 (141 bytes): signed by the payer

| Offset | Size | Field | Rule |
|---|---|---|---|
| 0 | 16 | prefix | ASCII `LOKA-PAY-NOTE-V1` |
| 16 | 32 | program id | equals the deployment's program id |
| 48 | 1 | cluster id | 0 devnet, 1 mainnet; equals the deployment's cluster |
| 49 | 32 | mint | equals the deployment's mint |
| 81 | 8 | allowance id | `u64` |
| 89 | 32 | payee key hash | key hash of the merchant's P-256 key |
| 121 | 8 | amount | `u64`, mint base units, greater than 0 |
| 129 | 3 | currency | ASCII `USD` |
| 132 | 1 | serial | `u8`, 0 to 255, unique per allowance |
| 133 | 8 | expiry | `i64` unix seconds; at most the allowance's expiry |

**Note wire (238 bytes):** `NOTE_V1 (141) || signature (64) || payer compressed public key (33)`.

Units: devnet USDC has 6 decimals, so $1.00 is 1,000,000 base units. Screens convert for display; every on-chain amount is in base units (`units` in the vectors).

### 4.2 ACK_V1 (56 bytes): signed by the merchant

| Offset | Size | Field |
|---|---|---|
| 0 | 16 | ASCII `LOKA-PAY-ACKN-V1` |
| 16 | 32 | note id |
| 48 | 8 | received at (`i64` unix seconds, the merchant phone's clock) |

**Ack wire (153 bytes):** `ACK_V1 (56) || signature (64) || merchant compressed public key (33)`. The merchant key's hash must equal the note's payee key hash. The note id already binds program, cluster and mint.

### 4.3 CONF_V1 (139 bytes): signed by the server

| Offset | Size | Field | Rule |
|---|---|---|---|
| 0 | 16 | ASCII `LOKA-PAY-CONF-V1` | |
| 16 | 32 | note id | |
| 48 | 64 | Solana transaction signature | all zeros when status is 3 |
| 112 | 8 | slot | `u64`; 0 when status is 3 |
| 120 | 8 | block time | `i64` unix seconds of that slot; 0 when status is 3 |
| 128 | 8 | uploaded at | `i64` unix seconds when the server received the upload (server clock) |
| 136 | 1 | status | 1 settled, 2 failed on chain, 3 refused before reaching the chain |
| 137 | 2 | error code | `u16`; the redeem_note Custom code when representable at status 2; 0 means no representable code, or any other status |

**Conf wire (203 bytes):** `CONF_V1 (139) || Ed25519 signature (64)`.

- Status 1 is sent once the transaction reaches `confirmed` commitment.
- The deliberate cheat (a second note on a used serial) is sent with preflight skipped so it lands as a failed transaction: status 2 with the program's named error, and the transaction signature opens on the explorer.
- Timing figures (task 3.41) use only signed times, and each names its two clocks:
  - **held offline** = CONF uploaded at minus ACK received at (server clock minus the merchant phone's clock);
  - **settled after upload** = CONF block time minus CONF uploaded at (chain time minus server clock);
  - **receipt to settlement** = CONF block time minus ACK received at.

  The merchant uploads as soon as it has signal, so "uploaded at" is the closest signed stand-in for "signal returned", and copy says "after upload", never "after signal". Clock skew between the phone, the server and the chain is a stated limitation.

### 4.4 Earmark list

`u16 count || count x 32-byte merchant key hashes`, sorted ascending by byte value, no duplicates, at most 16 entries. Count 0 means the allowance can pay any merchant. The **earmark hash** is `sha256` of those bytes.

### 4.5 ALLOW_V1 (185 bytes): allowance certificate, signed by the server

| Offset | Size | Field |
|---|---|---|
| 0 | 16 | ASCII `LOKA-PAY-ALLW-V1` |
| 16 | 32 | program id |
| 48 | 1 | cluster id |
| 49 | 32 | mint |
| 81 | 8 | allowance id (`u64`) |
| 89 | 32 | payer key hash |
| 121 | 8 | cap (`u64` base units): the most this allowance can ever settle |
| 129 | 8 | offline limit (`u64` base units): the most unsettled value one merchant should accept from this allowance |
| 137 | 8 | expiry (`i64`) |
| 145 | 32 | earmark hash |
| 177 | 8 | bond (`u64` base units) |

**Allowance wire:** `ALLOW_V1 (185) || Ed25519 signature (64) || earmark list (2 + 32 x count)`. A receiver recomputes the earmark hash from the attached list and rejects a mismatch.

The certificate mirrors the on-chain allowance account; the chain is the final judge. The offline limit is a merchant-side rule: the merchant app durably reserves each accepted note against it, survives a relaunch, and refuses a note that would take the cumulative unsettled value past it (task 2.20). The program does not enforce the offline limit.

### 4.6 MERCH_V1 (115 + name bytes): merchant certificate, signed by the server

| Offset | Size | Field |
|---|---|---|
| 0 | 16 | ASCII `LOKA-PAY-MRCH-V1` |
| 16 | 32 | program id |
| 48 | 1 | cluster id |
| 49 | 32 | mint |
| 81 | 32 | merchant key hash |
| 113 | 2 | name length `L` (`u16`), 1 to 64 |
| 115 | L | display name, UTF-8, Unicode NFC |

**Merchant wire:** `MERCH_V1 || Ed25519 signature (64)`.

### 4.7 WITHDRAW_V1 (161 bytes): signed by the merchant

| Offset | Size | Field |
|---|---|---|
| 0 | 16 | ASCII `LOKA-PAY-WDRW-V1` |
| 16 | 32 | program id |
| 48 | 1 | cluster id |
| 49 | 32 | mint |
| 81 | 32 | merchant key hash |
| 113 | 32 | destination wallet (a Solana address) |
| 145 | 8 | amount (`u64` base units) |
| 153 | 8 | withdraw counter (`u64`): equals the merchant record's current counter; the program adds 1 on success |

The program transfers only to the destination's associated token account for the configured mint.

### 4.8 REFUND_V1 (137 bytes, T3): signed by the merchant

| Offset | Size | Field |
|---|---|---|
| 0 | 16 | ASCII `LOKA-PAY-RFND-V1` |
| 16 | 32 | program id |
| 48 | 1 | cluster id |
| 49 | 32 | mint |
| 81 | 32 | original note id |
| 113 | 8 | allowance id (`u64`) |
| 121 | 8 | amount (`u64` base units) |
| 129 | 8 | refund counter (`u64`): equals the original note's refund record counter; the program adds 1 on success |

The program checks, in one instruction that either fully succeeds or changes nothing:

1. The original note's redemption record exists and names this merchant (its key hash signs the refund).
2. The refund's allowance id equals the allowance id in that redemption record. The credit goes to the allowance named by the record, never to one the request chooses.
3. The refund counter equals the record's current refund counter, which then advances by 1. A replayed refund carries a used counter and is refused, so it cannot debit the merchant twice.
4. Cumulative refunds for that note, including this one, never exceed the original amount.

Tests: a replayed refund leaves every balance unchanged; a refund naming a different allowance id is refused; a refund from another merchant is refused; an excess refund is refused.

### 4.9 Unsigned bundles

- **Spend marker (`M`):** `note wire (238) || ack wire (153)`. A valid note proves only that the holder of its signing key signed it, not that this key controls the allowance. So a phone shows "Conflicting spend seen" only when it holds a verified allowance certificate for that allowance id and BOTH notes (the marker's and its own) pass section 6, carry that allowance id and serial, have different note ids, and have a payer key whose hash equals the certificate's payer key hash. Only such a pair is an equivocation proof; on chain, `equivocation_proof` (task 3.5) checks both notes against the payer key stored in the allowance account.
- **Receipt (`X`):** `note wire (238) || ack wire (153) || flag (u8: 0 no confirmation attached, 1 confirmation attached) || conf wire (203, only when the flag is 1)`. A receipt with a confirmation is 595 bytes. The flag only says whether a CONF is present; it never means "settled". A verifier shows a status only after all of these hold: the note passes section 6; the ACK verifies, its note id equals the note id and its key hash equals the note's payee key hash; when a CONF is attached, its Ed25519 signature verifies with the pinned server key and its note id equals the note id. The displayed status comes from the CONF's status field (1 settled, 2 failed on chain, 3 refused); with no CONF it is "pending". A failed or refused confirmation is carried the same way, with flag 1. Receipt links put the base64url bytes in the URL fragment, never the query string: `https://zerobars.us/verify#r=<base64url>`, so the receipt never reaches a server log.

## 5. Transport

Payment content travels as the plaintext of an ordinary encrypted LOKA packet (v3 carrier chain), alongside LOKA's other content families:

```
L1|P|1|<kind>|<payload>
```

- `<kind>` is one ASCII letter: `N` note wire, `Y` ack wire, `S` conf wire, `M` spend marker, `X` receipt, `A` allowance wire, `C` merchant wire.
- `<payload>` is the bytes in base64url (RFC 4648 section 5) with no padding. Decoders reject padding, characters outside the alphabet, and non-canonical encodings (decode, re-encode, and compare).
- The text wrapper is never signed; every signature is inside the payload.
- An unknown version or kind is ignored and never relayed as payment content.
- Payment content from a peer that is not a contact is accepted with a payment-only scope (task 2.2): it can carry `L1|P` and nothing else.

Largest payloads: a receipt with a confirmation (595 bytes, 794 base64url characters) and an allowance with 16 earmarks (763 bytes). Both fit LOKA's packet plaintext limit with room to spare.

## 6. Validating a note

Every verifier (merchant phone, server, web page) runs these checks in this order and reports the first failure by its name. The `invalidNotes` vectors use the same names.

| Order | Check | Error |
|---|---|---|
| 1 | Wire is exactly 238 bytes | `length` |
| 2 | Prefix is `LOKA-PAY-NOTE-V1` | `prefix` |
| 3 | Cluster id equals the deployment's (0 devnet, 1 mainnet) | `cluster` |
| 4 | Currency is `USD` | `currency` |
| 5 | Amount is greater than 0 | `amount_zero` |
| 6 | Program id equals the deployment's | `wrong_program` |
| 7 | Mint equals the deployment's | `wrong_mint` |
| 8 | Public key decodes as a compressed P-256 point | `bad_pubkey` |
| 9 | `s <= n / 2` | `high_s` |
| 10 | ECDSA verifies over the 141 note bytes (`r` and `s` in range) | `bad_signature` |

Steps 3, 6 and 7 compare against the deployment's values from `config/pins.json`; the vectors use cluster 0, the vector program id and the devnet USDC mint in `constants`. Decoders do not check time.

**Merchant checks before showing "Received"** (after the table above, all must hold, using a verified allowance certificate, section 4.5):

1. The certificate's program id, cluster id and mint equal the deployment's (checked when the certificate is verified).
2. The certificate's allowance id equals the note's allowance id.
3. The certificate's payer key hash equals the key hash of the note's payer public key.
4. The note's payee key hash is this merchant's key hash, and it is in the certificate's earmark list when that list is not empty.
5. The phone clock is at most the note's expiry, and the note's expiry is at most the certificate's expiry.
6. The serial is not already in this merchant's ledger for this allowance.
7. Accepting the note keeps this merchant's cumulative unsettled value for the allowance at or under the offline limit (task 2.20).

The program checks everything in section 8.

## 7. Settlement transaction (Solana)

The secp256r1 precompile (program id `Secp256r1SigVerify1111111111111111111111111`) verifies the payer's signature. Precompiles cannot be called through CPI, so the program reads the precompile instruction through the instructions sysvar.

**Transaction shape:** compute-budget instructions (explicit limits, task 3.50), then the precompile instruction, then `redeem_note` immediately after it.

**Precompile instruction data for one note (254 bytes):**

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | number of signatures = 1 |
| 1 | 1 | padding = 0 |
| 2 | 2 | signature offset = 49 (`u16` little-endian) |
| 4 | 2 | signature instruction index = `0xFFFF` (this instruction) |
| 6 | 2 | public key offset = 16 |
| 8 | 2 | public key instruction index = `0xFFFF` |
| 10 | 2 | message offset = 113 |
| 12 | 2 | message size = 141 |
| 14 | 2 | message instruction index = `0xFFFF` |
| 16 | 33 | payer compressed public key |
| 49 | 64 | signature (low-S) |
| 113 | 141 | NOTE_V1 |

This matches the Solana SDK's own helper layout (public key, then signature, then message). Each vector note carries its `precompileDataHex`. A batch (task 3.25) puts several signatures in one precompile instruction, in the same order as the notes in `redeem_batch`.

## 8. What the program checks (`redeem_note`)

The program owner (task 1.4) implements these; the list is here so the server, phones and web agree on what "settled" means.

1. The instructions sysvar account is the canonical one (`Sysvar1nstructions1111111111111111111111111`), enforced by an address constraint, and instructions are read only with the checked loaders (`load_current_index_checked`, `load_instruction_at_checked`), which reject any other account.
2. The instruction before `redeem_note` is the secp256r1 precompile (program id checked), with one signature and all three instruction indexes `0xFFFF`.
3. The precompile message is exactly the 141-byte note passed to `redeem_note`, and the precompile public key equals the allowance account's stored payer key.
4. The note itself passes the stateless rules on chain: prefix `LOKA-PAY-NOTE-V1`, currency `USD`, amount greater than 0, program id equal to this program, cluster id equal to this deployment's, mint equal to the configured mint. The precompile proves only who signed the bytes, not that they are a well-formed note.
5. The allowance account is the program-owned PDA for the note's allowance id; the merchant record is the PDA for the note's payee key hash.
6. The serial's bit in the allowance's 256-bit used-bitmap is clear; redeeming sets it.
7. Total redeemed plus this amount is at most the cap.
8. The chain clock is at most the note's expiry and at most the allowance's expiry.
9. If the earmark list is not empty, the payee key hash is in it.
10. The merchant record is credited and an event is emitted.

The program tests (`programs/loka_vault/tests/redeem.ts`, task 1.4) must include correctly signed notes that break each of rule 4's conditions, a substituted instructions sysvar account, and a precompile instruction with two signatures.

PDA seeds are chosen by the program owner and recorded in `config/pins.json` and `programs/` once deployed; this document does not fix them.

**Fallback (D2):** if on-chain P-256 verification is not green at the Sat 3 AM checkpoint, the server verifies the note off-chain and `redeem_note` accepts only the server's Ed25519 attestation through the native Ed25519 program. The note format does not change.

## 9. Passkey notes from the web (T2, task 3.23)

A web payer signs the same NOTE_V1 with a passkey. The WebAuthn challenge is the note id. The precompile message becomes `authenticatorData || sha256(clientDataJSON)`, which is what ES256 signs. `redeem_note_webauthn` takes the full clientDataJSON as instruction data, hashes it on chain, compares it with the last 32 bytes of the precompile message, and checks: type `webauthn.get`, origin `https://zerobars.us`, challenge equal to base64url(note id), RP ID hash equal to `sha256("zerobars.us")`, the user-present and user-verified flags, and that the passkey is the one registered for the allowance. DER signatures from the browser are converted to 64-byte low-S. This section is a plan until task 3.23 passes its tests.

## 10. What this protocol does not promise

- Double spending is bounded, not prevented. The chain refuses a reused serial, so the payer can never settle more than the cap. A merchant who accepts a note offline carries the risk that the payer spent that serial elsewhere first, limited by the offline limit. Spend markers warn nearby merchants, and the bond (T2) repays a victim up to the bond.
- The merchant's received-at time is the merchant phone's clock. It is signed by the merchant, not proven.
- Relays carry packets they cannot read or change; the protocol does not hide that a payment happened from the public chain, which stores key hashes, amounts and times.
