# Chat content v1 — experimental text, voice and receipts

This is an application content version inside the existing authenticated, encrypted packet-v0 text field. Outer serialization, signatures, AAD, keys and five-minute expiry are unchanged. Both endpoints require the new build for voice/receipts; legacy ordinary text remains readable. Older apps may display structured content as text and do not acknowledge it. No automatic capability negotiation is claimed.

ASCII fields separated by `|`, starting `L1`. UUIDs are canonical lower-case. Standard padded Base64 is canonical; reject malformed encodings. Every wire content remains at most 2,048 UTF-8 bytes.

- `L1|T|<logical UUID>|<base64 UTF-8>`: text, 1–1,400 decoded bytes.
- `L1|V|<logical UUID>|<zero-based index>|<count>|<base64 bytes>`: MPEG-4 AAC-LC voice, chunks of up to 1,024 bytes, at most 32 chunks / 32 KiB. Recording stops after 12 seconds or the size cap. Partial assemblies are keyed by authenticated sender plus logical UUID, bounded to 8 assemblies, expire at the earliest constituent packet expiry, and reject conflicting chunks/counts.
- `L1|A|<logical UUID>`: destination acknowledgement. Accept only from the trusted destination of an existing outgoing logical message. Means the receiving app saved the complete message locally, not that a human read it. Never acknowledge acknowledgements.

Receipts contain no claimed geographic distance, path, hop count or read state. Lost receipts leave delivery unconfirmed even if content arrived. The UI must say 'Not confirmed', not claim nondelivery. Outgoing text/voice is encrypted and queued under one logical UUID; notification replies use the same path. Duplicate logical content must not create duplicate bubbles/notifications. An already saved incoming message can be acknowledged again on retry.

Pending packet ciphertext is bounded and retained only until original expiry; retries use identical packet bytes and IDs. Retries are paced and bounded by expiry, with at most four packets attempted per maintenance turn. No backend/Internet requirement is added.

Receipt packets are attempted on available links and immediately removed from the origin pending queue. They are rate-limited per logical message (three seconds, bounded cache). If a receipt is lost, a repeated data packet for the saved logical message can trigger another receipt. Relays still enforce the unchanged packet expiry and queue bounds. Outgoing messages retry at most four eligible packets per maintenance turn with at least 15 seconds between attempts. There is no exactly-once transaction across history, transport and OS notification actions; ordinary repeated send taps/actions are suppressed, while process death or storage failure during queue creation remains a fault-injection test requirement.

## Receipt recovery (0.6.6)

Both apps retain recipient-save receipts in the existing encrypted outgoing queue instead of discarding them immediately after submission. Existing queue limits (128 packets), expiry (five minutes), paced retry and reconnect replay apply. Receipt creation is suppressed for the same logical ID during that lifetime in each process; failed creation can be retried. Receipt packets never generate another receipt. No wire or cryptographic change.

On iOS, locked-screen ciphertext storage/notification is not a recipient-save receipt: the current private-key/history protection requires unlock before decryption and complete-message persistence. This change repairs lost receipt retries; it does not remove that locked-screen limitation or prove continuous background execution.

Image attachments/compression are not implemented. Encryption adds authentication overhead rather than shrinking data. Future image support needs bounded dimensions/encoded bytes, orientation handling, chunk validation and negotiated content support before encryption; do not inject compressed data into the existing text type or change the v0 codec silently. Existing voice notes already use AAC encoding before encryption.

## 0.6.13 media extension — updated endpoints required

Outer packet-v0 encoding, signing, encryption, expiry, packet size, relay hop limits and trust admission are unchanged. Text and receipts retain their existing encodings. This experimental content extension is **not capability-negotiated**: update both endpoints before sending images or voice notes above the former 32-chunk limit. Older receivers reject unsupported content; a local queue/sending indicator never means Delivered.

- Voice `L1|V|id|index|count|base64`: raised to 96 chunks / 96 KiB total. Native AAC-LC, mono, 16 kHz, requested 12 kbps, up to 60 seconds. Encoders can vary; the byte cap remains enforced. Android also stops at its recorder file-size limit; iOS rejects oversized completed output. Actual audio quality and full-duration phone-to-phone delivery still require hardware tests.
- Image `L1|I|id|index|count|base64`: at most 64 chunks / 64 KiB. Each nonfinal chunk is exactly 1024 bytes. Only 8-bit baseline/progressive JPEG with declared dimensions at most 1024 × 1024 is admitted. Sender resizes and re-encodes, discarding original image metadata; a preview requires explicit Send photo. Source selection is capped at 16 MiB. There are no captions, full-resolution originals, animations or photo-profile updates in this extension.
- Reassembly keys include sender, media kind and logical ID. Existing limit of eight assemblies and earliest-packet expiry remain. Image header/size bounds are checked after assembly before persistence/acknowledgement. Platform decoders handle rendering; header validation is not a complete JPEG decoder.
- Media uses the existing encrypted history, bounded outbox, retry and authenticated recipient-save acknowledgement path. Origin queue preflight stays at 120 packets, preserving headroom under the 128-packet hard cap. A large attachment can consume much of that budget; compression cannot guarantee fast BLE delivery.
- Android binary history export advances to version 3 with an image flag and continues reading versions 1/2. Stored row JSON uses optional image=false for old rows. iOS uses an optional image flag to retain compatibility with existing archives. Older apps cannot restore new image archives. Maximum stored Base64 body is 131072 bytes; Android encrypted row cap includes bounded JSON escaping/packet-ID overhead.

AAC is retained for native cross-platform support, not claimed to be universally optimal. References: [Android media formats](https://developer.android.com/media/platform/supported-formats), [Apple encoder bitrate setting](https://developer.apple.com/documentation/avfaudio/avencoderbitratekey). Opus remains a measured comparison to conduct before changing the codec/container contract.

## 0.6.14 message info and reactions

Both endpoints need 0.6.14 for these experimental content extensions. There is no capability negotiation. Released 0.6.13 decoders reject unknown H/R content, while unchanged A receipts and ordinary messages continue working. Packet-v0 encryption, keys, signatures and routing are unchanged.

- `L1|H|logical-id|hops`: recipient's report of the received packet counter, an integer 1–7. Direct delivery is one hop; relay count is hops minus one. Send separately after saving the message, alongside the unchanged A receipt. Accept only for an outgoing message addressed to the authenticated sender. H is not itself delivery confirmation and never triggers another receipt. Store the first report. Older history has no report.
- For chunked media, H describes the packet that completed reassembly, not the complete path of every chunk or the highest hop count. Relays can modify the v0 counter without invalidating its signature. The recipient authenticates its report, **not the correctness of the path**. Consumer info must say “Reported hops,” explain the estimate and show unavailable when absent. Never use H to score routes or claim a verified relay chain.
- `L1|R|event-id|base64(target-logical-id + "|" + emoji)`: reaction update. Target and event IDs are canonical UUIDs. Allowed values: 👍, ❤️, 😂, 😮, 😢, 🙏, or empty to remove. The target must already exist in the conversation with that authenticated sender. No new bubble or notification is created for a reaction. Unsupported/unknown targets are dropped.
- One reaction per participant per message. Order updates by the authenticated outer packet creation time, then canonical event ID; older retries cannot replace a newer reaction/removal. Empty reaction tombstones remain with history. Clock rollback can affect ordering; this is not a multi-device account reaction protocol.
- Acknowledge a persisted R with `L1|A|event-id`. Only a matching conversation partner can confirm an outgoing reaction. This clears its pending packet, without changing the original message's delivery state. Replacing a local reaction discards its prior pending packet. Reaction updates use the existing encrypted bounded outbox, retry, expiry and trust gates. Pending/expired confirmation remains visible in message info; no read receipts are implied.
- Android encrypted history stores optional metadata and binary backup format 4 stores bounded JSON message records; versions 1–3 remain readable. iOS archive fields are optional for compatibility. New backup exports require the new Android reader.

## 0.6.15 read confirmations

`L1|B|logical-id|viewed-at-ms` reports that a saved message appeared in its recipient's active conversation viewport. Timestamp is canonical nonnegative signed-64-bit decimal; reject reports more than 30 seconds after the signed envelope creation time. Acceptance requires an existing outgoing message addressed to the authenticated sender. A read confirmation also establishes delivery; it never confirms another conversation or a reaction. No confirmation is emitted merely for a notification, background receipt, lock-screen storage or opening an offscreen conversation item. Displaying a voice-note bubble is read status, not playback/listened status.

Persist the local viewed timestamp before creating the receipt. A bounded maintenance pass retries creating unqueued read receipts (at most four per pass, origin queue headroom preserved), then the existing encrypted outbox retries identical B packets for their five-minute envelope lifetime. B receipts do not trigger receipts of their own. Once that retry window expires, remote read status may remain unconfirmed. Reading old saved content can create a fresh B envelope with its recorded viewed timestamp; clocks remain subject to the existing packet-v0 validation rules.

Delivery time is the earliest received recipient-save/read receipt envelope creation time, not the sender's arrival time. Read time is the recipient's reported viewed timestamp. Optional archive fields retain compatibility with old history, whose confirmed delivery may lack an exact time. Blue double ticks mean a read confirmation was received; grey double ticks mean delivery was confirmed. These are device reports and cannot prove human comprehension.
