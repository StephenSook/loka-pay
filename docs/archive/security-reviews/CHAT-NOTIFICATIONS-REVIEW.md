# Chat content, persistence and notifications — internal design review

2026-10-02. Reviewer: Codex (implementation author). Scope explicitly requested: experimental local notifications/replies, recorded voice notes and truthful delivery status on both native apps. This is an internal design review, not independent production approval. Existing experimental v0 risks and lack of forward secrecy remain.

Before implementation, reviewed: outer packet bytes/crypto stay unchanged; typed content is encrypted and signed by existing v0. Receipt acceptance binds authenticated sender to the locally stored intended recipient and unpredictable logical ID. Receipts are only generated after successful local save and never for another receipt. A dishonest recipient can acknowledge its own messages; receipts are not human read proof. Relays cannot generate a valid receipt as the destination. No hop/geographic progress is inferred.

Voice reassembly has per-transfer/global caps, strict canonical parsing, duplicate/conflict rejection, a short recording limit and expiry. Decoder errors must be visible without crashing; audio is played only after a user action. Temporary microphone files stay app-private, are deleted on cancellation/send/disposal and are not backed up. No background recording or new cloud dependency.

Android uses its existing AES-GCM/Keystore history protection for voice content and status, expanding bounded record size. iOS history uses a separate random 256-bit Keychain key and CryptoKit AES-GCM authenticated encryption, atomic writes, bounded file size, no key regeneration over existing history and no private identity exports. Existing identity remains WhenUnlockedThisDeviceOnly; do not weaken key accessibility for background convenience. Locked iPhone handling must defer private operations, retain only bounded verified ciphertext, and require unlock for replies.

Notification text defaults to a generic message, avoiding private content on the lock screen. Notifications are generated only for authenticated trusted incoming messages (or verified ciphertext awaiting unlock), never relayed traffic. Explicit notification permission; per-conversation grouping and IDs; Reply/Open chat actions; recheck trust, payload limits and identity availability for every reply. Android receiver is not exported and PendingIntents are explicit; only RemoteInput reply intents are mutable. iOS reply actions require authentication. Outgoing replies are protected against duplicate action handling and use the same send queue as the composer.

Background scope: user-started Android connectedDevice foreground service with a visible notification and explicit Off; iOS bluetooth-central restoration for a previously selected connection. Neither bypasses force-stop, locked private keys, OS scheduling or radio/permission restrictions. Physical screen-off/background delivery and voice latency remain gates, not claims.

Required verification: cross-language content vectors, malformed limits, sender-bound receipts, voice reorder/duplicates/conflicts/expiry, persistence tamper/failure, restart/expiry behavior, duplicate send guard, builds/lint, isolated notification/UI checks and physical testing without Internet. No user keys/history may be exported or wiped for tests.

Implementation verification: 32 core tests, 10 isolated Android instrumentation tests, Java/Swift interop, native Swift archive tamper/restart and bounded voice tests passed; signed builds/lint passed. This remains an author review. Physical background/voice tests and crash/storage-failure injection are outstanding; no exactly-once transaction across platform action, history and transport is claimed. Temporary recording/playback files are removed on next process startup after an interrupted session.

Reconnect follow-up: remember only the previously user-selected iPhone peripheral after a successful public probe, never label its identifier as authenticated contact identity. Restoration/reconnect still gates packets on a new probe and leaves Android approval intact. Explicit Off cancels reconnect; failure backoff is bounded and a single OS-managed pending connection may wait for the selected peer. No new peer is automatically selected, no new contact trusted, and no crypto/key accessibility changes are made.
