# LP1 internal security review

Scope: enabling direct-link profile exchange and explicit chat consent in the experimental Android/iOS apps. Uses existing RSA3072/AES-GCM packet-v0 operations, without new cryptographic algorithms or key accessibility changes. Not an independent audit or production security certification.

Required implementation checks: signatures/destination/time validated before content handling; profile tied to a live challenge; LC1 peer key matches the verified profile; discovery alone never imports trust; bounded admission before decrypt; encrypted durable consent/block state with save-before-side-effects and fail-closed behavior; persistent revocation; retry keeps deadline; no control relaying; received names never overwrite local aliases. UI must identify names as self-chosen, not account verification. Anonymous relay can remain enabled while people visibility is off. Hide stale profiles when links close and use fresh RSSI only.

Residual risks: stable public keys are linkable; a malicious neighbor can relay a handshake and does not prove physical adjacency; rotating attacker keys are not prevented by per-key blocks; packet-v0 has no forward secrecy; device clock errors affect expiry; two contact stores cannot commit atomically across phones. A successful native link/profile does not prove end-to-end delivery. Real-device profile/consent and radio reliability require separate measurement.

Disposition: integrate with software regression and interoperability checks for this experimental build. No weakening of the chat trusted-sender predicate or private-key protection is authorized by this review.

## Internal review: encrypted typing extension (0.6.29)

Reviewed the new LP1 typing admission against the existing trust boundary: signature and recipient verification precede the new control branch; a matching link profile alone is insufficient, and the app supplies its actual trusted-contact predicate. No draft text, stored activity history, forwarding, push notification or delivery acknowledgement is created. Canonical timestamp/state parsing, short expiry, replay ordering and bounded rate/state limit stale UI and resource use. UI departure, background and idle stop are best effort; receiver expiry is mandatory. This reveals current activity to an already approved contact and retains existing traffic metadata exposure. It does not change message encryption or establish reliable realtime calling. Tests cover untrusted rejection, throttle, stop ordering, replay, expiry and a slow profile exchange. This is an internal engineering review, not an independent protocol audit.


## Internal boundary review — Apple Wi-Fi Aware experiment 0.6.30

The new route accepts only WiFiAware-produced endpoints/connections and confirms an Aware path after the fixed magic exchange. Apple's system pairing is link admission only: existing packet signature/recipient checks and trusted-contact checks remain mandatory; LP1 profile challenge and consent remain unchanged. TCP carries existing encrypted application envelopes and native paired Aware supplies link security. No new app key format, plaintext chat protocol, trust import or cloud dependency is introduced. Read/write/setup deadlines, one active channel, a 32-frame queue and 16-KiB frame cap bound this experiment. Background scheduling can defer timers; no hard realtime guarantee is implied. Opt-in entitled signing is separate from the normal disabled build. Android's PSK experiment is explicitly not treated as native paired interoperability. Code/build/regression evidence does not establish hardware delivery; native pairing and device-to-device frame transfer remain experimental gates.

## Internal review: bundled avatar metadata (0.6.57)

Reviewed the optional LP1 I control against the existing profile and consent boundary. It uses the unchanged signed, recipient-encrypted packet envelope and requires the current accepted per-link profile key and challenge nonce before applying an exact 42-ID whitelist. Per-link canonical timestamp ordering and 60-second freshness reject stale/replayed metadata; disconnect resets ephemeral nonce/timestamp state. Profile withdrawal makes further metadata inadmissible. Own visibility off prevents avatar sends, including changed selections. The ID is a catalog lookup, never a filesystem path or URL. Custom photos do not enter this channel. Maps inherit the 32-link bound and existing global 32-controls/10-second admission.

The metadata can reveal a chosen illustration to people already entitled to receive the chosen nearby name. It is self-asserted and proves neither real-world identity nor physical proximity. Friends may cache a last-known catalog ID by already trusted device key; other nearby entries expire with their links. There is no new trust import, consent shortcut, cipher, key export, message wire schema, broadcast payload or forwarding behavior. Swiping left invokes the existing Decline operation; swiping right/Later hides only the local card and never sends acceptance. Accept remains explicit. Clock skew and best-effort control loss can leave a fallback/old portrait until another exchange. This internal engineering review is not an independent audit.

Required validation: native Kotlin/Swift initial/change/clear exchange, malformed ID/nonce/time and replay rejection, visibility and disconnect boundaries, old-peer optional-control compatibility, unchanged consent/typing regressions and actual Kotlin–Swift interoperability. Physical profile/avatar propagation still needs hardware observation; software exchange alone is not radio proof.

Final compatibility checks also ran the previous Kotlin LP1 implementation against updated Swift, and previous Swift LP1 against updated Kotlin. Both request directions retained names, consent and typing while older receivers ignored the optional avatar control. Multi-link display checks retain the newest accepted avatar for one device identity; request ordering is stable by deadline and request ID. Final builds and 91 Kotlin core tests passed. After the Android phone reconnected, the final 0.6.57 (65) builds, including multi-link avatar selection and stable request ordering, were installed in place on the Samsung SM-S948U1, iPhone SE (3rd generation) and iPad Air (5th generation). The Android emulator also received the final APK; isolated review devices were restored to regular builds. Existing device data was preserved.
