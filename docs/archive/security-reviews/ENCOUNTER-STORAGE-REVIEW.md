# Encounter storage implementation review — 2026-10-05

Scope: local shadow encounter persistence only. This is a scoped implementation review, not an independent cryptographic audit or approval of PRoPHET/gateway wire changes.

- Both platforms reuse established AES-GCM archive storage with randomized nonces and the existing platform-secured history key. The dedicated authenticated label `loka.encounters.v1` separates this record type from chat, nearby and carry ciphertext. No identity key, message encryption algorithm or signed packet is changed.
- Android stores one bounded encrypted blob in the existing history database, using SQLite replacement and the Android Keystore key. iOS uses an atomic file excluded from backup with complete file protection and the existing WhenUnlockedThisDeviceOnly archive key. No additional background-readable protection class is introduced for encounter relationships.
- Restore rejects duplicates, malformed identities, non-finite/out-of-range estimates, invalid counts/timestamps and excessive records before modifying in-memory state. Encoded/plain limits are 32 KiB plus GCM overhead; table cap remains 64. Expired and future-dated records are omitted. Restoration preserves the score's original timestamp, avoiding double aging; active sessions never persist.
- A storage authentication/validation failure disables further writes for that process. The existing encrypted blob is preserved; ordinary chat/carry functionality remains independent. This fail-closed storage policy is not a data-recovery mechanism. Unlocking can resume normal protected saves; a genuine storage error requires diagnosis/restart.
- Only aggregate record count is emitted in development diagnostics. Full authenticated device IDs are present inside the encrypted local record, which constitutes relationship metadata. No prediction table, public advertisement, contact upload or cloud backup is added. Explicit app-data deletion removes this storage with the existing database/application-support cleanup.
- Writes occur only when raw bounded records change, not on each two-second tick or continuously changing decay snapshot. Expiry cleanup occurs when the app executes; it cannot guarantee physical deletion at the exact expiry instant while the OS suspends the process.
- Tests cover native restore/age/requalification, invalid restore preserving old state, Swift archive restart and tamper rejection, and an isolated Android Keystore/database instrumentation test. Physical lock/reboot/deletion and performance measurements remain separate work.

Outstanding: encounter opt-out/settings policy, protected persistence failure recovery UX, identity-rotation/linkability policy and privacy-reviewed transitive summaries. Prediction remains shadow-only; none of these records grants friendship, carrier delegation, copy allowance or remote mailbox authority.
