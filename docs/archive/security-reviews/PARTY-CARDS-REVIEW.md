# Party Cards session authorization review

Scope: preserve the current encrypted packet formats, algorithms, signatures, routing and relay authorization. Introduce a default-deny application authorization callback for non-contact encrypted game events. Chat's existing trust predicate stays unchanged.

At send, a non-contact recipient must have a verified signed nearby profile or belong to the saved accepted game session. At receive, verify the existing packet signature/expiry/path before decrypting, require a known candidate identity before decrypting non-contact traffic, then authorize only strictly parsed Party Cards events. The game engine separately validates version, exact catalog hash, invitation expiry, session, roster, explicit acceptance, turn and revision. Discovery permits an invitation; it never creates session membership. No public key is imported into chat contacts. Unsupported game payloads and all chat content from non-contacts remain rejected.

Persist accepted session identity/public-key associations in the existing protected game archive, separately from contacts. Maximum one session, four devices, bounded invitations/events/log/storage and 120-second envelopes. All deliveries retain ordinary priority and the chat queue reserve. Relays continue to see ciphertext only. Future/hidden quiz/card secrets are outside this party-prompt game; content is bundled locally and card IDs are exchanged.

Required validation: non-contact games succeed only through scoped authorization; non-contact chat and malformed/unsupported events still fail; membership without acceptance fails; chat interoperability is unchanged; expiry, duplicates, conflicting snapshots, host pause/recovery, queues and protected restart behavior remain bounded. This is an implementation threat review, not independent security certification. Malicious-host resistance and measured mesh capacity are not claimed.

Implementation bounds: four-device fixed roster, one accepted session, 24 actions, 12 pending events, 16 KiB engine state / 32 KiB protected owner archive. The existing AES-GCM storage key is reused with a distinct `loka.party.v1` authenticated namespace; chat and Quiz archive namespaces remain separate. Protected owner state persists at most three member public keys, validated against device fingerprints. Restoration permits only exact pending packet IDs and destinations. Received invitation replay IDs remain bounded and persisted until expiry. Changes to public-key associations roll back if invitation validation fails. Account reset clears all in-memory game permissions.

At owner restart, discard own queued ciphertext whose destination no longer has chat trust or an exact persisted game-packet permission. Relay frames still undergo the existing authorization checks. Transient non-contact capability/ACK replies are regenerated on duplicate/recovery rather than causing an entire queue restore to fail. Persisted proposals/commits remain scoped and recover through snapshots.

Catalog 3.1 adds explicit adult/drinking restrictions; existing G2 eligibility also excludes alcohol prompts unless drinking is enabled. The UI gates that option at self-declared 21+. Local filtered-deck eligibility is a UX check, not cryptographically attested age or malicious-client protection. New live filter synchronization is not implemented by G2. No cryptographic algorithm or outer encrypted packet format changed for the local deck.
