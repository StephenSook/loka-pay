# Message info and reactions review — 0.6.14

Internal implementation review, not an independent security audit. This content extension preserves existing packet-v0 cryptography, trusted-sender admission and relay behavior. It adds no shared friendship private key. Each endpoint retains its own device private key; each packet uses a fresh AES key wrapped for the recipient. Existing lack of forward secrecy remains.

H reports are bounded 1–7, matched against both an outgoing logical message and its intended recipient. They do not mark delivery. The sender cannot mistake the receipt's own return hop counter for the original packet's reported counter. However v0 hop metadata is mutable: the UI explicitly labels it an estimate, with final-reassembly-packet scope for media. No names, addresses or relay identity lists are disclosed.

R updates require an existing target in the same authenticated sender conversation; data is restricted to a UUID and six supported emojis/removal. Stored reactions are bounded to one per participant plus version metadata. Message arrival notifications are not generated. Timestamp/event-ID ordering handles replay/reordering; persisted empty tombstones prevent old reactions reappearing after removal. Existing envelope lifetime bounds, signature verification and queue limits apply. Missing targets are dropped rather than growing an orphan inbox.

Acknowledgements match the latest local reaction event and conversation peer. They do not acknowledge a different person's reaction or mark a text/photo/voice message delivered by association. Failed saves must not generate success receipts. History fields are stored under existing encryption; backups require the new format reader. Clipboard copying is explicit and applies only to text.

Remaining limitations: no feature negotiation, no independently verified hop path, no multi-device reaction merge, wall-clock ordering assumes a reasonably stable sender clock, and no atomic transaction across network submission/history/outbox writes. A reaction can reach the recipient during a local persistence failure; the UI must not promise exactly-once distributed edits. Physical reaction/hop-report interoperability remains a separate hardware test.

## 0.6.15 receipt and attachment follow-up

Internal review permits the requested read-confirmation content extension with unchanged encryption and sender admission. B reports are matched against the outgoing logical ID and intended recipient, timestamps are canonical/bounded, and implausibly future reports are rejected. Incoming read state is persisted before receipt generation. Visibility comes from the active conversation's viewport and foreground lifecycle, not notification delivery. Message info describes short device-reported status; the protocol retains the full limits. B is not echoed/acknowledged, so receipt loops are not introduced. Queues and expiry remain bounded; report creation retries use a dedicated lock rather than holding the ViewModel monitor across engine calls.

Camera captures are explicit, permission-gated, previewed and compressed through the same bounded JPEG path as library images. Android's nonexported FileProvider exposes only the capture cache subdirectory with temporary URI access; completed/cancelled captures are deleted, and abandoned captures are cleaned up after one hour. No general file or photo-library permission is added. iPhone uses a native photo-only camera picker with explicit cancel and in-memory downscaling before bounded re-encoding; LOKA does not save captures to the photo library automatically. Physical camera/permission/cancellation behavior remains a device test.
